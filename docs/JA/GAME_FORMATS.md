# ゲームごとのStreetPassメッセージ形式

StreetPassで運ばれるメッセージ(TMP Box)の共通部分(ヘッダ、HMACトレーラー等)は
[PROTOCOL_REFERENCE.md](PROTOCOL_REFERENCE.md)にまとめてある。ここでは、その
**本文(body)の中身がタイトルごとにどう違うか**を扱う。公開資料(3dbrew等)には
本文の形式は書かれておらず、各タイトルの実行コードを自分で吸い出して静的・動的解析で
読み解く必要がある。

このファイルの内容は、いずれも自分が所有するソフトのダンプを自分で解析して得た結果。
実行コード本体や鍵は含まない。

## 1. メッセージの識別

StreetPassの「サービス」は5バイトのIDで識別される(3dbrewの
[StreetPass](https://www.3dbrew.org/wiki/StreetPass)ページ参照): 先頭4バイトが
タイトルIDの下位32bit、末尾1バイトが送信方式等のフラグ。

| タイトル | サービスID(先頭4バイト) | 備考 |
|---|---|---|
| StreetPass Mii Plaza | `00 02 08 00` | 本プロジェクトが対象にしている主なタイトル |
| とびだせ どうぶつの森 | `00 19 8D 00` | 3dbrewの記載(EUR)。日本版のamiibo+版も下位32bitが一致することを確認 |
| リッジレーサー | `00 03 58 00` | 3dbrewの記載 |
| ザ・シムズ3 | `00 03 65 00` | 3dbrewの記載 |
| ストリートファイター | `00 03 05 00` | 3dbrewの記載 |
| ともだちコレクション 新生活(EUR) | `00 08 C5 00` | 3dbrewの記載 |

メッセージ種別が1タイトルに複数ある場合は、`CecMessageHeader`の`userData`フィールド
(オフセット0x6E)で区別するタイトルがある(とびだせ どうぶつの森がそう)。

## 2. StreetPass Mii Plazaの受理判定

受信したメッセージについて、Mii Plazaは次の順で検査する。**どれか1つでも失敗した
メッセージは何のエラーも出さずに読み飛ばされる**(緑ランプが点灯するだけで広場には
何も出ない)。

1. メッセージのmagicが`0x6060`、全体サイズが`0x19000`以下、bodyサイズが`0x45d8`以上
2. 本文の各フィールドを範囲内に丸める(範囲外は0にするだけで拒否はしない)
3. body `0x36bc`から始まる送信者のMiiデータベースを取り込む:
   - ヘッダのmagicが`"CFPB"`(製品版。開発版は`"CFPN"`)
   - body `0x36d4`から**0x70バイト**のエントリを、システムの`APT:Unwrap`
     (コマンド`0x00470104`、入力0x70/出力0x60/nonceオフセット0xC/nonce長10)で復号。
     **ここでAES-CCMの認証タグ16バイト全体が検証される**
   - 続いてCRC16、`mii_id`が全ゼロでないこと、`mii_id[0] & 0x20 == 0`、CharInfoの
     全フィールドの範囲チェック(名前に`%`や`\`を含まない等)
4. 送信者の`author_id`(8バイト)を、1000件のテーブル(1件12バイト、状態値が7以外で
   該当)と照合し、見つかれば拒否(ブロックリストらしいが、テーブルの出所は未確認)
5. 通過したら訪問者として登録。既知の訪問者なら保存済みのMii(0x60バイト)と比較して
   「内容が変わった」フラグを立てるが、これは拒否条件ではない

このため、Miiの顔・ニックネーム・`author_id`/`mii_id`を自由に書き換えても、**手順3の
認証タグを書き換え後の内容に対して正しく再計算しさえすれば**受理される。なお、
Miiブロックを108バイト(タグ先頭12バイトまで)と誤解して書き換えると、タグ末尾4バイトが
元のBoxの値のまま残り、全ての改変Miiが手順3で黙って破棄される——このプロジェクトで
最も長く原因が分からなかった問題だった。

## 3. とびだせ どうぶつの森

**調査状況: 実行コードの静的解析のみ。実機から採取した本物のメッセージによる裏付けは
まだ行っていない。** オフセットの一部はコミュニティで知られるセーブデータの
配置と一致するように見えるが、記憶ベースで照合していない。

### 3.1 送受信の仕組み

ゲームは`nn::cec::CTR::MessageBox`クラス(RTTI文字列で確認)経由でCECDサービス
(`cecd:u`/`cecd:s`)を使い、自前のメッセージボックスを持つ。CECタイトルIDは`0x198d`
(`0x00198d00`)、groupId=1。

SDKのCECD IPCコマンドのヘッダ値(3dbrewにも記載):

| コマンド | ヘッダ値 |
|---|---|
| ReadMessage | `0x00030104` |
| WriteMessage | `0x00060104` |
| OpenAndRead | `0x00120104` |
| OpenAndWrite | `0x00110104` |
| ReadMessageWithHMAC | `0x00040106` |
| WriteMessageWithHMAC | `0x00070106` |
| Delete | `0x00080102` |
| ReadData | `0x000A00C4` |

送信は`Message::NewMessage` → `SetMessageBody` → `SetExHeader`(id=2: アイコン、
id=4: UTF-16LE文字列)→ `MessageBox::WriteMessage`の順。受信は受信箱の全メッセージを
`userData`で振り分け、**本文サイズが固定値と完全一致しないものは破棄**する。

### 3.2 メッセージ種別1(`userData=1`): 家+プレイヤー(本文0x7DC8バイト)

おそらく「ハッピーホームショーケース」の家データ交換。

| 本文offset | サイズ | 内容 |
|---|---|---|
| 0x0000 | 4 | magic `0x0700009E` |
| 0x0004 | 4 | CRC-32C(Castagnoli、多項式`0x82F63B78`の反転、init/xorout=`0xFFFFFFFF`)。対象は0x0008から0x7DC0バイト |
| 0x0008 | 8 | u64(ID系と推測、未特定) |
| 0x0010 | 0x1228 | 家データ(セーブ内のプレイヤー別領域`+0x5d900 + i*0x1228`からコピー) |
| 0x1238 | 0x6B88 | プレイヤーデータ(先頭0x6B88バイトをコピー。`+0x5498`の0xA8バイトは送信時に再エンコード) |
| 0x7DC0 | 8 | セーブ`+0x6e29a`由来の8バイト(未特定) |

受信側はmagicとCRCを検証し、本文`+0x67de`/`+0x67f4`(u16)/`+0x67f6`(18バイト)/`+0x6808`を
自分のセーブの対応位置と比較して、**同じ村からのメッセージは取り込まない**。

### 3.3 メッセージ種別2(`userData=2`): 引っ越し住民(本文0x2520バイト、送信は1回限り)

| 本文offset | サイズ | 内容 |
|---|---|---|
| 0x0000 | 4 | CRC-32C(対象は0x0004から0x251Cバイト) |
| 0x0004 | 4 | 状態 = 2(送信可能) |
| 0x0008 | 0x2518 | 住民データ1体分 |

受信時は住民ID(住民データ内`+0x2C`)などを検証したうえで保存領域へ書き込む。

### 3.4 解析上の注意

- 実行コード(`.code`)の**ファイル内オフセットとGhidra上の仮想アドレス(VA)は
  `+0x00100000`ずれる**。生バイト列検索の結果をそのまま逆アセンブルしないこと。
- Ghidraの自動解析で、`exit`系の関数が誤ってnoreturn扱いになり後続コードが関数として
  認識されない箇所がある。noreturnを外して関数を作り直すと読める。

# 実機なしでBoxを確認する: Mii Plazaのエミュレータテスト

3DS実機もWi-Fiも使わずに、TMP Boxを**Mii Plazaが受理するか**を確認できます。AzaharPlus
(3DSエミュレータ)上で本物のMii Plazaを動かし、すれちがい受信箱にBoxを入れて、ゲームの
反応を見る方法です。「Boxに本当に必要な領域はどこか」を調べたのもこの方法で、
`scripts/build_tmp_box.py`で作ったBoxを実機に近づける前に試す一番手軽な手段です。

## 分かること・分からないこと

- **Mii Plaza自身の受信処理を試せます**: ヘッダ確認、ブロックリスト、本文のサニタイズ、
  Mii取り込み、訪問者登録。この部分はエミュレータ上でも改造なしの本物のコードが動きます
- **システムサービス(CECD)は試せません**: AzaharPlusはCECDを独自に再実装しているため、
  メッセージ認証(HMACトレーラー)や無線層は通りません。ここで受理されても、実機では正しい
  HMACが別途必要です(`build_tmp_box.py`は常に計算します)
- 訪問者の「見た目」は、エミュレータ画面で見える範囲のことしか分かりません

## 必要なもの

(全用途のソフトウェア一覧は[REQUIREMENTS.md](REQUIREMENTS.md)にあります。)

- Linux上の**AzaharPlus**(暗号化タイトルを直接起動できるフォーク)
- **自分の実機のMii Plaza**: ベースタイトルの`.app`(NCCH)と、SDカードにあるアップデート
  タイトル(日本版は`0004000E00020800`。`--trace`の受信側アドレスはこのアップデート版のもの)。
  GodMode9などで自分でダンプしてください
- `Xvfb`、ImageMagick(`import`)、Python 3.10+。`--trace`には`gdb-multiarch`も

## 最初に1回だけ行う準備

1. アップデートタイトルのTMDとコンテンツを、AzaharPlusのSDタイトル置き場に置く:
   `<azaharのデータ>/sdmc/Nintendo 3DS/<id0>/<id1>/title/0004000e/00020800/content/`
   (`00000000.tmd`と`.app`群。SDの暗号層は外した状態)
2. ベースの`.app`を一度起動する(`AzaharPlus <mii_plaza_base.app>`)。初回はMii Plazaが
   SDデータを作り、いくつかのダイアログが出るので、広場が出るまでAボタン(既定のキー割り当て
   では`S`キー)で進める
3. エミュレータを閉じ、**この状態をベースラインとして保存**する: エミュレータの`nand/`と、
   `sdmc/Nintendo 3DS/<id0>/<id1>/`の下の`extdata`。テストは毎回これを復元するので、前回の
   訪問者や途中のミニゲームが結果に影響しません
4. `--trace`でゲストの動作を読むには、エミュレータのGDBスタブ(ポート24689)を有効にする

## テストの実行

```bash
python scripts/emu_receiver_test.py box.bin \
    --azahar /path/to/AppRun-or-AppImage --app mii_plaza_base.app \
    --baseline /path/to/baseline --trace
```

ベースラインを復元し、CEC受信箱にBoxを入れ(`scripts/emu_inject_inbox.py`)、仮想ディスプレイで
エミュレータを起動し、待ってからスクリーンショットを撮って結果を表示します。

| 結果 | 画面 | `--trace` |
|---|---|---|
| **受理** | 「今回のすれちがい N回 やった!!」 | `ヘッダ読み → ブロックリスト → ヘッダ読み → サニタイズ → Mii取り込み → ブロックリスト → 訪問者登録` |
| **拒否**(例: MiiのCCMタグを1バイト変えた) | 無関係なダイアログ(「ところで…」) | `ヘッダ読み`で止まる |

本物のBoxは受理され、MiiタグだけをこわしたBoxは実機と同じように黙って捨てられます
(ランプは点くが広場に訪問者は出ない)。

## Boxに必要な最小限を調べる: `emu_bisect_box.py`

```bash
python scripts/emu_bisect_box.py genuine_box.bin --azahar ... --app ... --baseline ... [--combine]
```

本文の領域(タイトル、アイコン、国名/地域名、コメント、コンソール固有の記録、末尾の統計、
居住地コード)を1つずつゼロにして、ACCEPT/rejectを表示します。本物のBoxでの結果:
**どの領域も単独でゼロにできて、本文先頭0x30バイトと送信者Mii以外を全部ゼロにしたBoxも
受理されました。** 本文の地図は[PROTOCOL_REFERENCE.md](PROTOCOL_REFERENCE.md)を参照。

## なぜ監視スレッドが要るのか

Mii Plazaはメッセージを処理した後、受信箱を削除し、`InBox___/BoxInfo_____`の先頭0x20バイトを
**古いメッセージ件数のまま**書き戻します。本物のCECDは件数を直しますが、エミュレータのCECDは
直さないため、ファイルが「ヘッダのみなのに1件」という矛盾した状態になり、次の読み出しで
ゲームがパニックします(`svcBreak`、ゲスト側の整合性検査が返す`0xC8E1086A`)。テストスクリプトは
このファイルを監視し、数ミリ秒以内に件数を0に戻します。これが無いと、受理されたBoxでも
直後にエミュレートされたゲームが落ちます。

## 限界

- `--trace`の受信側アドレスは1つのビルド(日本版アップデート)用です。他のリージョンには
  別のアドレスが必要ですが、スクリーンショットでの判定はそのまま使えます
- **受理は実機と一致しているが、到着時の会話は細部が違う**: これまでの実機テストと受理/拒否は全て一致したが、会話については、エミュレータは初対面でコメントと趣味を一度に出すのに対し、実機はプロフィールの一文を1〜2個(コメントは出ず)、同じMiiは1日1回の会話だった。
- エミュレータでは共有Miiデータとフォントにオープンソースの代用品が使われるため、顔は
  プレースホルダーで表示されます。見た目ではなく受理/拒否で判断してください
